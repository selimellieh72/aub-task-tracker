# Reflection

During this project I used Claude Code inside my editor to generate code, implement the backend and frontend changes, write tests, and update the project documentation. I used Claude mainly to plan the work, write structured prompts for Claude Code, and check that each step followed the assignment. I sent one focused prompt at a time — inspect the project, user stories, backend, tests, frontend, review — inspected every change, and re-prompted when something needed fixing. This kept me in control of what went into the repository.

Three of the assumptions I reviewed up front shaped the result more than any code. Where should "overdue" be computed? I chose the backend, as a computed field, so it became a boolean I could test with pytest instead of a JavaScript date comparison; the break test that removed the "Done is never overdue" clause failed two tests from two angles. Should tags be normalized, and where? Server-side only — trim, lowercase, dedupe — so `Bug` and `bug` become one chip and there is exactly one set of rules to test. Should the planning notes be committed? Claude recommended it; I decided to keep the repository to code, tests, and the required documentation.

One moment where AI was particularly helpful was the first prompt, which asked Claude Code to inspect the project before changing anything. It found, before a line was written, that an existing test asserts the exact set of response keys and that `update_task` already distinguishes "omitted" from `null`. Both facts went straight into the implementation prompt, so clearing a due date needed no new mechanism and the key-set test was updated deliberately instead of being discovered red.

One moment where AI slowed me down was the backend Tags step. Claude Code finished with 41 green tests and then reported that `PATCH {"tags": null}` returned `tags: null`, contradicting the contract — but left it alone because my prompt said "no special-casing". Correct obedience, wrong outcome. I had to read the storage code myself, recognise the same `model_copy` hole that the existing `description` guard plugs, and add the fix and its test. Over-constraining the prompt cost a round trip.

A place where my own review changed the final result was the review prompt for the Tags feature. Claude Code found that a tag containing a comma, which the API accepts, is silently split into two tags when the task is edited in the modal. I fixed it on the backend by rejecting commas, making the UI's delimiter part of the contract. I also rejected one "should-fix" from the same review — a failed refetch after a filtered drag wiping the board — because it is the app's pre-existing failure mode and the fix would have duplicated filter logic in the browser. Finally, manual testing caught something no test did: changing the tag filter flashed the loading banner and shifted the filter bar. Reading the state-handling code myself led to a small quiet-refetch fix rather than a layout change.
